# 目标导向设计全流程

## R — 原文 (Reading)

> "本书提供了一组方法来解决这种以行为为导向的新型设计，并提供完整的设计过程，从而更好地理解用户目标、需求和动机，我们称为'目标导向设计'。设计应当先于写代码和测试工作。"
>
> — Alan Cooper, 第1章

---

## I — 方法论骨架 (Interpretation)

目标导向设计是一套完整的交互设计方法论，核心思想是"目标驱动而非功能驱动"。

流程分6个阶段：
1. **研究**：用情境调查法深入理解用户真实行为和目标
2. **建模**：从研究数据中构造人物模型（Persona），锚定设计对象
3. **场景**：用叙事场景设想理想交互，从场景提炼设计需求
4. **框架**：定义产品形式、姿态、功能元素，勾画交互框架
5. **提炼**：用设计原则和模式不断细化交互细节
6. **支持**：设计师在开发阶段持续支持，确保设计意图不被稀释

关键前提：设计师和开发者角色分离，设计先于编码。产品行为应该是设计决策的结果，而非编码的副产品。

## A1 — 书中的应用 (Past Application)

### 案例 1: 视频编辑产品用户研究
- **问题**: 客户想为"有摄像机和电脑但未连接二者"的用户开发入门视频编辑软件，市场研究显示重大商机
- **方法论的使用**: 用目标导向设计的研究阶段，对12名目标用户进行实地访谈
- **结论**: 12人中只有1人能成功连接摄像机和电脑（还需IT人士帮助），产品成功的必要前提不存在
- **结果**: 帮助客户决定搁置产品开发，省下大笔投资

### 案例 2: 数字产品行为恶劣的诊断
- **问题**: 为什么大多数数字产品难用、令人恼火？
- **方法论的使用**: 用目标导向设计诊断根本原因——重点错置、无视用户、利益冲突、设计流程缺失
- **结论**: 产品行为恶劣不是技术问题，是流程问题。需要独立的设计角色和系统化的设计方法
- **结果**: 提出目标导向设计方法论作为解决方案

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 从零开始设计一个数字产品的交互，不知道从何入手
2. 产品功能很多但用户抱怨难用，需要系统性改进
3. 做了用户研究但不知道如何把研究结论转化为设计方案
4. 产品开发团队中设计师和开发者角色混淆，设计沦为编码的副产品

### 语言信号 (用户的话里出现这些就应激活)

- "怎么设计这个产品的交互？"
- "功能很多但用户不会用"
- "用户研究结果怎么变成设计方案？"
- "产品体验差不知道从哪改起"
- "设计和开发应该谁先谁后？"

## E — 可执行步骤 (Execution)

1. **定义设计挑战**
   - 明确产品是什么、为谁设计、商业目标是什么
   - 完成标准：能用一句话说清"为[谁]设计[什么]，帮助他们达成[什么目标]"

2. **研究用户（情境调查）**
   - 在用户真实环境中观察和访谈6-8个精心挑选的用户
   - 完成标准：收集到用户行为模式、目标和痛点的定性数据

3. **构造人物模型**
   - 从研究数据中综合出1个主要人物模型+1-2个次要人物模型
   - 完成标准：每个模型有名字、目标、行为特征，能回答"她会怎么做？"
   - 判停条件：若资源极有限，跳过完整8步法，用临时人物模型（1页描述+目标）

4. **创建场景并提炼需求**
   - 用人物模型创建情境场景，从场景提炼设计需求
   - 完成标准：至少3个关键路径场景 + 需求列表（需求≠功能）

5. **定义框架**
   - 确定产品形式要素、姿态、功能元素分组，勾画交互框架
   - 完成标准：白板级别的交互框架草图 + 关键路径场景验证通过

6. **提炼并支持开发**
   - 用设计原则和模式细化交互细节，在开发阶段持续支持
   - 完成标准：设计规格文档 + 开发过程中的设计评审通过

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯视觉/UI设计（不涉及交互行为）→ 用视觉设计方法
- 纯技术架构设计（不涉及用户交互）→ 用软件工程方法
- 已有清晰交互方案只需执行 → 直接执行，不需要方法论
- 资源极少的快速原型验证 → 用简化版（临时人物模型+快速场景）

### 作者在书中警告的失败模式

- **功能列表驱动设计**: 把需求文档当功能列表，认为功能越多越好，产品变成功能堆砌
- **混淆领域知识和设计知识**: 让领域专家或用户直接设计界面，他们能描述问题但想不出好的解决方案
- **设计是编码的副产品**: 没有独立设计角色，产品行为由开发者的技术决策决定

### 作者的盲点 / 时代局限

- 方法论偏向有预算、有团队的中大型项目，对独立开发者/小团队适用性存疑
- 对敏捷开发批评较尖锐，未充分考虑敏捷与目标导向设计融合的可能
- 缺乏对数据驱动设计（A/B测试、增长黑客）的讨论

### 容易混淆的邻近方法论

- 设计思维（Design Thinking）: 更宽泛的创意方法论，目标导向设计更聚焦于数字产品交互
- 以用户为中心的设计（UCD）: 目标导向设计是UCD的一种具体实现，但更强调"目标"而非"需求"
