# 目标vs任务区分法

## R — 原文 (Reading)

> "目标是对最终结果的预期，任务是达成目标的中间步骤。大多数产品关注任务而忽视目标。设计满足情境中的目标而非任务清单，因为任务可能随技术变化，但目标相对稳定。"
>
> — Alan Cooper, 第1章

---

## I — 方法论骨架 (Interpretation)

目标和任务是两个不同层次：
- **目标**：用户想要达成的最终结果（为什么做）——相对稳定
- **任务**：达成目标的具体步骤（做什么）——随技术变化

用户目标分三层：
1. **体验目标**：用户想感受什么（如"不觉得自己蠢""不无聊"）
2. **最终目标**：用户想完成什么（如"快速找到航班""安全转账"）
3. **人生目标**：用户想成为什么（如"成为好父母""被认可为专家"）

区分的实际价值：
- 只看任务→优化现有流程（更快地完成错误的事）
- 看目标→可能发现全新的解决方案（用不同方式达成同一目标）

## A1 — 书中的应用 (Past Application)

### 案例 1: 航空公司订票系统
- **问题**: 早期订票系统让用户一步步完成"查航班→选航班→填信息→付款"的任务流程
- **方法论的使用**: 区分任务（查航班、比价、订票）和目标（找到最合适的出行方案）
- **结论**: 用户的目标不是"订票"，是"安排最佳出行"。如果系统能理解"最佳"的标准（时间、价格、舒适度），可以主动推荐而非让用户逐一搜索
- **结果**: 指导设计从"任务流程优化"转向"目标导向推荐"

### 案例 2: 体验目标驱动设计
- **问题**: 为什么某些功能完善的产品仍然让用户感到挫败？
- **方法论的使用**: 识别体验目标——用户不只是想"完成任务"，还想"不觉得自己蠢""不焦虑""有掌控感"
- **结论**: 即使功能正确，如果交互让用户觉得自己蠢（如晦涩的错误消息），体验目标未被满足
- **结果**: 体验目标成为设计质量的重要衡量标准

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 产品功能齐全但用户仍不满意——可能满足了任务但没满足目标
2. 需求文档写的是任务列表而非用户目标
3. 需要判断某个功能是否真正必要——它服务于什么目标？
4. 技术变革导致现有任务过时——用户的目标变了吗？

### 语言信号

- "用户到底想要什么？"
- "功能和目标的区别是什么？"
- "为什么有了这个功能用户还是不满意？"
- "需求怎么从任务提炼到目标？"
- "这个功能真的有必要吗？"

### 与相邻 skill 的区分

- 与 `persona-construction` 的区别: persona构造用户模型，本skill在模型中识别目标层次
- 与 `scenario-driven-design` 的区别: 场景从目标出发设计交互，本skill确保你找到了正确的目标

## E — 可执行步骤 (Execution)

1. **列出用户任务**
   - 写下用户目前为达成目的所做的所有步骤
   - 完成标准：有完整的任务清单

2. **逐层追问"为什么"**
   - 对每个任务问"为什么要做这个？"→ 得到最终目标
   - 对最终目标问"为什么这很重要？"→ 得到人生目标
   - 对每个操作问"做这个时想感受什么？"→ 得到体验目标
   - 完成标准：每个任务都有对应的三层目标

3. **检查目标-任务映射**
   - 是否有任务没有对应目标？（可能是冗余功能）
   - 是否有目标没有对应任务？（可能是未被满足的需求）
   - 完成标准：目标-任务映射完整且无冗余

4. **用目标重新设计**
   - 忘掉现有任务，只看目标，问"还有什么更好的方式达成这个目标？"
   - 完成标准：至少提出1个不基于现有任务的新方案

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯技术实现问题（不涉及用户动机）→ 技术方案不需要目标分析
- 任务明确且目标显而易见的简单操作 → 过度分析反而浪费时间
- 系统间接口设计（不涉及用户）→ 用技术规范

### 作者在书中警告的失败模式

- **任务驱动设计**: 只优化现有流程，不质疑流程本身是否必要
- **混淆目标和任务**: "用户需要搜索功能"是任务，"用户需要快速找到想要的信息"才是目标
- **忽视体验目标**: 只关注功能目标，忽视用户的情感需求

### 作者的盲点 / 时代局限

- 某些场景下用户自己也无法清晰表达目标，需要更深入的研究方法
- B2B产品中，购买者（决策者）和使用者的目标可能不同甚至冲突
- 缺乏对无意识目标（用户未意识到但影响行为的动机）的讨论

### 容易混淆的邻近方法论

- Jobs to be Done (JTBD): 同样关注"为什么"，但JTBD聚焦"雇佣产品完成的任务"，本框架区分目标层次
- 根因分析 (5 Whys): 追问原因的方法类似，但本框架特指用户目标的三层分类
