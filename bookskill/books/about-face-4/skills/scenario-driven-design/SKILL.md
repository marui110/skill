# 场景驱动设计法

## R — 原文 (Reading)

> "场景是关于人及其活动的简明叙述性语言，是一种生成式工具。设计需求不是特性——需求是用户需要完成的，特性是产品如何满足需求。场景从人物模型的目标出发，而非从功能列表出发。"
>
> — Alan Cooper, 第4章

---

## I — 方法论骨架 (Interpretation)

场景是用叙事连接用户研究和产品设计的桥梁。

三类场景：
1. **情境场景**：描述人物模型在理想世界中如何与产品交互，不受技术限制——用于探索可能性
2. **关键路径场景**：描述用户完成核心任务的详细步骤——用于验证设计框架
3. **验证场景**：用次要人物模型或边缘场景测试框架的完整性——用于发现遗漏

从场景到需求的关键转换：需求≠功能。需求描述"用户需要什么"，功能描述"产品怎么做"。

场景 vs 用例 vs 用户故事：
- 用例：系统视角，描述系统响应
- 用户故事：需求条目，"作为X我想Y"
- 场景：叙事设计工具，描述人的完整体验

## A1 — 书中的应用 (Past Application)

### 案例 1: iPhone日历与来电冲突
- **问题**: 用户正在查看日历时来了电话，如何处理两个任务的冲突？
- **方法论的使用**: 用场景叙事描述完整情境——用户正在查看明天日程安排，突然来电打断
- **结论**: 从场景推导出设计需求"用户需要同时处理两个任务而不丢失上下文"，而非功能"来电弹窗"
- **结果**: iPhone的设计方案是顶部横幅通知而非全屏弹窗，保留了日历上下文

### 案例 2: 从场景提炼设计需求
- **问题**: 如何确保设计需求来自用户目标而非开发者的想象？
- **方法论的使用**: 先写情境场景（人物模型的一天），再从场景中提取需求
- **结论**: 场景保证需求有用户行为佐证，避免"开发者觉得用户需要"的臆想
- **结果**: 产出需求列表，每条需求都能追溯到场景中的用户行为

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 有了人物模型但不知道如何设计具体交互行为
2. 需要从用户目标推导设计需求，而非从功能列表出发
3. 团队在"需求"和"功能"之间混淆，需求文档写的是功能列表
4. 需要验证设计方案是否真正满足用户目标

### 语言信号

- "怎么从用户研究到设计方案？"
- "需求怎么提炼？"
- "场景和用例有什么区别？"
- "设计需求怎么写才不是功能列表？"
- "怎么确保设计满足用户目标？"

### 与相邻 skill 的区分

- 与 `goal-directed-design` 的区别: 本skill聚焦场景创建和需求提炼，goal-directed-design是全流程
- 与 `persona-construction` 的区别: persona产出"用户是谁"，场景产出"用户怎么用"
- 与 `product-posture` 的区别: posture决定产品姿态，场景决定具体交互流程

## E — 可执行步骤 (Execution)

1. **创建情境场景**
   - 用主要人物模型写1-2个情境场景：她的一天、她如何与产品交互
   - 不受技术限制，描述理想体验
   - 完成标准：场景是完整叙事（有开头、过程、结果），不是功能列表

2. **从场景提炼设计需求**
   - 逐句扫描场景，提取"用户需要X"的陈述
   - 区分需求（用户需要什么）和功能（产品怎么做）
   - 完成标准：需求列表中每条都能追溯到场景中的具体行为

3. **创建关键路径场景**
   - 对每个核心需求，描述用户完成任务的详细步骤
   - 用交互框架草图验证场景可行性
   - 完成标准：每个核心需求有对应的关键路径场景

4. **用验证场景测试**
   - 用次要人物模型跑关键路径场景，发现遗漏
   - 用边缘场景测试框架的鲁棒性
   - 完成标准：次要人物模型和边缘场景都被覆盖

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已有明确功能列表且团队认可 → 直接进入框架设计
- 纯技术需求（如性能、安全）→ 技术需求不需要场景驱动
- 系统间接口设计（不涉及用户交互）→ 用API设计方法

### 作者在书中警告的失败模式

- **场景变成功能列表**: 把场景写成"用户点击X，系统显示Y"——这是用例不是场景
- **需求=功能**: "用户需要搜索功能"是功能不是需求，"用户需要快速找到想要的信息"才是需求
- **场景脱离人物模型**: 场景必须从具体人物模型出发，不是"用户"的抽象行为

### 作者的盲点 / 时代局限

- 场景方法对叙事能力有要求，不是所有团队成员都擅长写场景
- 在快速迭代环境中，完整的三类场景可能过于重流程
- 缺乏对数据驱动场景（基于用户行为数据构造场景）的讨论

### 容易混淆的邻近方法论

- 用例（Use Case）: 系统视角，关注系统响应；场景是人的视角，关注体验
- 用户故事（User Story）: 需求条目格式；场景是叙事设计工具
- 故事板（Storyboard）: 场景的可视化形式，但场景本身是文本叙事
