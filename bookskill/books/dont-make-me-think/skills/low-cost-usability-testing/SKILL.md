## R (原文)

> "测试3个用户就能发现大约85%的可用性问题。"
> 
> "可用性测试不需要昂贵的实验室和大量用户，它可以简单、快速、非正式地进行。"
> 
> "测试越早越好，越早越便宜。"

## I (自述)

低成本可用性测试的核心是：不需要大量资源就能发现大部分可用性问题。关键在于尽早测试、频繁测试，而不是等到产品完成后再测试。

关键洞见：可用性问题发现得越早，修复成本越低。早期测试可以避免后期返工带来的巨大成本。

## A1 (书中案例)

**正面案例：某电商网站测试**
- 测试用户：3名目标用户
- 测试任务：完成一次购买流程
- 方法：边做边说
- 发现问题：优惠券入口不明显、结账按钮太小
- 改进效果：转化率提升25%

**反面案例：不做测试直接上线**
- 问题：用户找不到核心功能
- 结果：用户流失率高
- 成本：后期修复成本高

## A2 (触发场景)

| 场景 | 是否触发 | 理由 |
|------|----------|------|
| 产品迭代改进 | 是 | 需要验证改进效果 |
| 设计方案验证 | 是 | 需要用户反馈 |
| 资源有限 | 是 | 低成本方案 |
| 用户反馈问题 | 是 | 需要找到原因 |
| 需要统计数据 | 否 | 纯定量研究 |
| 无产品原型 | 否 | 无法测试 |

## E (可执行步骤)

### 步骤1：准备测试
- 定义测试任务（3-5个核心任务）
- 准备测试脚本
- 准备记录工具（纸笔即可）

### 步骤2：招募用户
- 招募3-5名目标用户
- 不需要专业用户
- 可以是同事、朋友

### 步骤3：进行测试
- 说明测试要求（边做边说）
- 用户执行任务
- 记录用户行为和言语

### 步骤4：分析结果
- 整理发现的问题
- 分类问题优先级
- 制定改进方案

### 步骤5：迭代改进
- 修复高优先级问题
- 再次测试
- 循环迭代

## B (边界)

### 适用范围
- 产品迭代测试
- 设计方案验证
- 用户体验优化
- 资源有限的团队

### 不适用范围
- 需要大规模统计数据
- 纯定量分析
- 无产品原型
- 需要专业实验室的研究

### 局限性
- 无法提供统计显著性
- 样本量小
- 结果可能有偏差
